# TMP Architecture Decisions (ADR)

**Document ID:** TMP-005  
**Status:** Accepted  
**Version:** 1.13

---

# 1. Назначение

Данный документ содержит ключевые архитектурные решения (Architecture Decision Records, ADR), принятые при проектировании TOP Manufacturing Platform (TMP).

Каждое решение фиксирует не только принятое правило, но и его контекст, причины выбора и последствия для дальнейшего развития платформы.

Документ является единым реестром архитектурных решений проекта и используется:

- архитекторами;
- разработчиками;
- техническими руководителями;
- при проектировании новых Capability;
- при анализе архитектурных изменений.

---

# 2. Назначение ADR

Architecture Decision Record (ADR) — запись о принятом архитектурном решении.

Каждый ADR описывает:

- проблему;
- контекст;
- принятое решение;
- последствия.

После получения статуса **Accepted** решение считается обязательным для всех новых компонентов платформы.

---

# 3. Статусы решений

| Статус | Описание |
|---------|----------|
| Proposed | Решение предложено и находится на обсуждении |
| Accepted | Решение утверждено и является обязательным |
| Superseded | Решение заменено более новым ADR |
| Deprecated | Решение больше не рекомендуется использовать |

---

# 4. Правила оформления ADR

Каждая запись содержит следующие разделы:

- Идентификатор;
- Название;
- Статус;
- Контекст;
- Решение;
- Последствия;
- Связанные документы.

Нумерация ADR является сквозной и никогда не изменяется.

Если решение заменяется новым, старое получает статус **Superseded**, но не удаляется из документа.

# ADR-001

## Название

Platform Core не содержит бизнес-логики.

### Статус

Accepted

### Контекст

TMP проектируется как модульная платформа, состоящая из независимых Capability.

При размещении бизнес-логики в Platform Core возникает сильная связанность компонентов и нарушение границ ответственности.

### Решение

Platform Core отвечает исключительно за инфраструктуру платформы.

Platform Core предоставляет:

- регистрацию Capability;
- жизненный цикл компонентов;
- маршрутизацию запросов;
- инфраструктурные сервисы;
- доступ к конфигурации;
- управление событиями.

Platform Core не содержит бизнес-правил.

### Последствия

Все бизнес-правила реализуются только внутри соответствующих Capability.

Добавление новой функциональности не требует изменения Platform Core.

# ADR-002

## Название

Capability является основной функциональной единицей TMP.

### Статус

Accepted

### Контекст

Платформа должна позволять независимо развивать различные функциональные области без изменения существующих компонентов.

### Решение

Каждая функциональная область реализуется как отдельная Capability.

Capability:

- имеет собственную область ответственности;
- владеет своими данными;
- публикует собственный API;
- регистрируется через Capability Engine;
- самостоятельно объявляет права и события.

### Последствия

Функциональные области становятся независимыми.

Добавление новой Capability не требует изменения существующих компонентов.

# ADR-003

## Название

Capability взаимодействуют только через публичные API.

### Статус

Accepted

### Контекст

Прямой доступ к внутренним данным другой Capability приводит к высокой связанности и невозможности безопасного развития системы.

### Решение

Ни одна Capability не имеет права изменять внутреннее состояние другой Capability напрямую.

Взаимодействие между Capability выполняется исключительно через публичные контракты владельца данных, разделённые по назначению (согласовано с Constitution принцип 28 и ADR-004):

- изменяющие межмодульные бизнес-операции — только через бизнес-документы Document Engine;
- синхронное чтение чужих данных — только через Public Query API владельца;
- асинхронное информирование о завершённых изменениях — только через Domain Events владельца.

Public Query API и Domain Events не могут использоваться для обхода document-driven изменения состояния. Изменяющие application-операции владельца не являются внешним Public API.

### Последствия

Каждая Capability полностью контролирует собственное состояние.

Изменение внутренней реализации не влияет на остальные части платформы.

Границы «чтение / изменение / уведомление» единообразны во всех спецификациях Capability.

### Связанные документы

- Platform-Core-Specification.md
- Capability-Engine-Specification.md
- TMP-Constitution.md

# ADR-004

## Название

Бизнес-документ является точкой входа бизнес-процесса.

### Статус

Accepted

### Контекст

Большинство операций платформы инициируется действиями пользователя и должно иметь полную историю изменений.

### Решение

Любой бизнес-процесс начинается с создания бизнес-документа.

Документ:

- содержит бизнес-смысл операции;
- проходит жизненный цикл;
- инициирует выполнение бизнес-логики;
- является источником пользовательской истории.

Изменяющие бизнес-операции выполняются только через проведение бизнес-документа. Public Query API (синхронное чтение) и Domain Events (асинхронное уведомление о завершённых изменениях) дополняют документную модель, но не могут использоваться для обхода document-driven изменения состояния (согласовано с Constitution принцип 28 и ADR-003).

### Последствия

История действий пользователя полностью сохраняется.

Выполнение процессов становится воспроизводимым и прослеживаемым.

### Связанные документы

- Document-Engine-Specification.md
- TMP-Constitution.md

# ADR-005

## Название

Warehouse является единственным владельцем складских остатков.

### Статус

Accepted

### Контекст

Складские остатки используются множеством функциональных областей платформы:

- Production;
- Procurement;
- Order Management;
- Inventory;
- Logistics.

Если несколько Capability смогут изменять остатки напрямую, неизбежно возникнут рассинхронизация данных, нарушение бизнес-правил и невозможность гарантировать корректность учета.

### Решение

Warehouse является единственным владельцем складских остатков.

Любое изменение запасов выполняется только через Warehouse.

Ни одна Capability не имеет права напрямую изменять:

- Stock Position;
- Warehouse Movement;
- Storage Cell;
- Stock State;
- Batch.

### Последствия

- централизованный контроль складского учета;
- единая история изменений;
- отсутствие конкурирующих механизмов изменения остатков.

### Связанные документы

- Warehouse-Specification.md

# ADR-006

## Название

Stock Position является текущим состоянием склада.

### Статус

Accepted

### Контекст

Необходимо разделить историю операций и текущее состояние склада.

### Решение

Stock Position хранит только текущее состояние запаса.

Stock Position определяется сочетанием:

- Material;
- Warehouse;
- Storage Cell;
- Stock State;
- Batch (при необходимости).

История изменений в Stock Position не хранится.

### Последствия

История и текущее состояние полностью разделены.

Обновление текущего остатка не требует анализа всей истории движений.

### Связанные документы

- Warehouse-Specification.md

# ADR-007

## Название

Warehouse Movement является неизменяемой записью истории.

### Статус

Accepted

### Контекст

История складских операций должна быть полностью прослеживаемой.

Изменение исторических записей делает невозможным проведение аудита и расследование ошибок.

### Решение

Warehouse Movement:

- создается только Warehouse;
- никогда не изменяется;
- никогда не удаляется.

Исправление ошибок выполняется только созданием новых Warehouse Movement.

### Последствия

История склада становится полностью воспроизводимой.

### Связанные документы

- Warehouse-Specification.md

# ADR-008

## Название

Любое изменение запасов выполняется через Warehouse Operation.

### Статус

Accepted

### Контекст

Разные бизнес-документы выполняют различные операции, но все они изменяют складские остатки.

### Решение

Все складские документы преобразуются в универсальный объект Warehouse Operation.

Warehouse выполняет только Warehouse Operation.

Тип документа значения не имеет.

### Последствия

Единый механизм выполнения всех складских операций.

Минимизация дублирования логики.

# ADR-009

## Название

Отрицательные остатки запрещены.

### Статус

Accepted

### Контекст

Отрицательные остатки приводят к недостоверному складскому учету.

### Решение

Перед выполнением Warehouse Operation Warehouse проверяет доступное количество.

При недостатке материалов операция отклоняется.

Warehouse Movement не создаются.

### Последствия

Складской учет всегда остается корректным.

# ADR-010

## Название

Передача материалов на склад производства выполняется в два этапа.

### Статус

Accepted

### Контекст

Передача материалов между складами не гарантирует моментального получения.

Необходимо учитывать материалы, находящиеся в пути.

### Решение

Передача на склад производства состоит из двух этапов:

1. Отгрузка.
2. Приемка.

После отгрузки материалы получают состояние `IN_TRANSIT`.

После подтверждения приемки материалы становятся доступны на складе производства.

### Последствия

Появляется возможность контролировать материалы, находящиеся в пути.

### Связанные документы

- Warehouse-Specification.md

# ADR-011

## Название

Резервирование является изменением состояния Stock Position.

### Статус

Accepted

### Контекст

Резервирование не должно создавать отдельную сущность хранения.

### Решение

Резервирование выполняется переводом количества:

```text
        │
        ▼

```

### Последствия

Резервирование становится обычной складской операцией.

# ADR-012

### Контекст

# ADR-014

## Название

Warehouse может разделять документ перемещения.

### Статус

Accepted

### Контекст

Иногда только часть строк документа может быть выполнена.

### Решение

Если документ невозможно выполнить полностью, Warehouse может предложить разделение.

Создаются:

- документ с исполнимыми строками;
- документ с проблемными строками.

Исходный документ получает статус `SPLIT`.

### Последствия

Частичное проведение не требуется.

Пользователь получает возможность продолжить работу без изменения исходного документа.

# ADR-016

## Название

В версии 1.0 используется пессимистическая блокировка.

### Статус

Accepted

### Контекст

На начальном этапе эксплуатации важнее простота и предсказуемость работы склада, чем максимальная масштабируемость.

### Решение

Во время выполнения Warehouse Operation необходимые Stock Position блокируются.

После завершения операции блокировки снимаются.

Архитектура должна позволять заменить механизм конкурентного доступа в будущих версиях без изменения публичного API.

### Последствия

Упрощается реализация и исключаются конфликты изменения остатков.

В дальнейшем возможен переход на оптимистическую блокировку без изменения внешнего поведения Warehouse.

# ADR-017

## Название

Позиция заказа является главным производственным объектом платформы.

### Статус

Accepted

### Контекст

Большинство ERP-систем используют заказ как основной объект производственного управления.

Однако в TMP различные изделия одного заказа могут:

- иметь разные спецификации;
- запускаться в производство независимо;
- выпускаться независимо;
- иметь собственные карты раскроя;
- иметь различные производственные статусы.

Использование заказа как основной единицы приводит к усложнению архитектуры и невозможности независимого управления изделиями.

### Решение

Главным производственным объектом TMP является **позиция заказа (Order Item)**.

Все производственные Capability работают исключительно с позициями заказа.

Заказ клиента используется только как контейнер коммерческой информации.

### Последствия

- упрощается архитектура Capability;
- исчезает необходимость хранить производственные данные заказа как источник истины;
- появляется возможность независимого управления состоянием изделий;
- значительно упрощается Production;
- значительно упрощается Warehouse;
- появляется возможность независимого планирования изделий.

> **Уточнение (ADR-033):** пользовательский workflow Production v2.1 работает с заказом целиком (принятие/отмена/агрегированный статус), но **хранимое** производственное состояние остаётся item-owned. ADR-017 не superseded.

### Связанные документы

- Production-Specification.md
- Warehouse-Specification.md

# ADR-018

## Название

Спецификация позиции заказа является неизменяемой.

### Статус

Accepted

### Контекст

Изменение спецификации после начала работы других Capability приводит к рассинхронизации данных.

Production, Warehouse, Cutting Optimization и будущий Procurement должны использовать единый источник данных.

### Решение

После утверждения Revision позиции заказа её Specification становится **Immutable**.

Изменение существующей Specification запрещено.

Любое изменение изделия выполняется созданием новой Revision позиции заказа либо новой позиции заказа.

### Последствия

- единый источник истины;
- отсутствует синхронизация между Capability;
- отсутствует необходимость создавать копии Specification;
- упрощается аудит;
- упрощается взаимодействие Capability;
- становится возможным безопасное версионирование изделий.

### Связанные документы

- Order-Management-Specification.md
- Production-Specification.md
- Warehouse-Specification.md
- Cutting-Optimization-Specification.md

# ADR-019

## Название

Каждая Capability владеет только собственными бизнес-данными.

### Статус

Accepted

### Контекст

По мере роста платформы возникает риск дублирования информации между Capability.

Например:

- Production может начать хранить складские остатки;
- Warehouse — производственные статусы;
- Order Management — производственные документы;
- Cutting Optimization — складские данные.

Это приводит к сильной связанности платформы.

### Решение

Каждая Capability является единственным владельцем собственных бизнес-данных.

Другие Capability используют их исключительно через Public API или Domain Events.

Capability не должна хранить копии чужих данных без отдельного архитектурного решения.

### Последствия

- отсутствует дублирование данных;
- снижается связанность;
- упрощается сопровождение;
- становится возможным независимое развитие Capability.

### Связанные документы

- TMP-Constitution.md
- Platform-Core-Specification.md

# ADR-020

## Название

Вычисляемые состояния не должны храниться.

### Статус

Accepted

### Контекст

Во многих информационных системах вычисляемые состояния сохраняются в базе данных.

Это приводит к рассинхронизации и необходимости постоянной синхронизации.

### Решение

Если состояние может быть вычислено из первичных данных, оно не хранится.

Например:

- завершённость производства заказа;
- готовность заказа;
- агрегированные статусы;
- аналитические показатели.

Исключения допускаются только отдельными архитектурными решениями.

### Последствия

- уменьшается объём хранимых данных;
- исключается рассинхронизация;
- упрощается архитектура Capability.

### Связанные документы

- Order-Management-Specification.md
- Production-Specification.md

# ADR-021

## Название

История бизнес-событий является неизменяемой.

### Статус

### Контекст

# ADR-023

## Название

Cutting Plan является независимым технологическим документом.

### Статус

Superseded (заменён ADR-034)

### Контекст

Производству требуется использовать результаты оптимизации раскроя без изменения спецификации изделия.

Попытка сохранять результаты раскроя внутри Specification или Production приводит к смешению ответственности различных Capability.

### Решение

Cutting Plan является самостоятельным бизнес-документом Capability Cutting Optimization.

- создаётся независимо от Production;
- не изменяет Specification;
- содержит только технологические данные раскроя;
- может иметь несколько Revision;
- используется Production только после утверждения.

### Последствия

- разделяются ответственность Production и Cutting Optimization;
- спецификация изделия остаётся неизменяемой;
- появляется возможность повторного расчёта без изменения изделия.

# ADR-028

## Название

Capability-owned Business Document Payload.

### Статус

Accepted

### Контекст

Document Engine владеет платформенным жизненным циклом документа и его metadata (`DocumentId`, тип, заголовок, автор, время создания, статус, операции `post`/`unpost`/`close`/`delete`, вызов зарегистрированного `DocumentProcessor`). Однако бизнес-содержимое документа конкретной Capability (например, состав заказа, спецификация позиции) является предметными данными и не должно попадать в Platform Core как произвольный domain JSON, иначе нарушаются границы владения (ADR-019) и типобезопасность.

Проверка фактического контракта Document Engine: `DocumentOperationContext.document()` предоставляет `DocumentMetadata` с `DocumentId` (`id()`); `DefaultDocumentEngine` аннотирован `@Transactional`, вызывает `DocumentProcessor.onPost(...)` внутри той же транзакции, что и изменение статуса документа и запись lifecycle-журнала, а Domain Events публикуются только после commit (`TransactionAfterCommitEventPublisher`). Атомарность processor-изменения и платформенного изменения документа гарантирована этой транзакционной границей.

### Решение

Document Engine владеет lifecycle и metadata документа. Capability владеет строго типизированным business payload своих документов.

1. Business payload не хранится в `DocumentMetadata` и не хранится в Platform Core как произвольный domain JSON.
2. Payload хранится Capability отдельно (собственный persistence port и adapter) и связывается с платформенным документом через `DocumentId`.
3. `DocumentProcessor` получает `DocumentId` из `DocumentOperationContext` и загружает типизированный payload из репозитория своей Capability.
4. Payload имеет версионируемую схему (`PayloadSchemaVersion`) и optimistic locking черновика (`PayloadRevision`).
5. Payload редактируется только внутренними application/UI use cases Capability, пока платформенный документ находится в редактируемом Draft-состоянии; после успешного проведения payload становится immutable.
6. Payload одной Capability нельзя читать или изменять напрямую из другой Capability; доступ к результатам — только через Public Query API и Domain Events владельца.
7. Обработка проведения должна быть идемпотентной (processing record с уникальностью `DocumentId + Operation`).
8. Атомарность изменения агрегата, записи processing record и изменения результата проведения обеспечивается транзакционной границей Document Engine (processor вызывается внутри транзакции проведения; события — после commit). Если для какой-либо Capability этот контракт окажется недостаточным, требуется отдельный prerequisite-ADR/задача до реализации её Document Processors.

### Последствия

- сохраняется типобезопасность и владение предметными данными (ADR-019);
- Platform Core остаётся свободным от предметного JSON;
- обеспечивается воспроизводимость, идемпотентность и неизменяемость проведённого содержимого;
- межмодульное взаимодействие остаётся document-driven (ADR-003, ADR-004, Constitution принцип 28).

### Связанные документы

- Document-Engine-Specification.md
- Order-Management-Specification.md
- TMP-Constitution.md

# ADR-029

## Название

Source-neutral Order Intake Boundary.

### Статус

Accepted

### Контекст

Order Management должен принимать данные заказа двумя MVP-каналами: ручной ввод и файловая выгрузка расчётной программы. В будущем теоретически возможен адаптер к Firebird «СуперОкна», но вероятность низка и реализация вне MVP. Домен Order Management, Document Processors и Public Query API не должны зависеть от формата файла, кодировки, JDBC Firebird, пути к файлу или схемы внешней СУБД. Прямая запись из UI или парсера в таблицы нарушает ADR-004 / Constitution принцип 28.

### Решение

1. Вводится граница: `External source → source adapter → source-neutral import model → Order Management application services / business documents`.
2. Source-neutral import model принадлежит Order Management application layer и не содержит зависимостей от `.stxt`, JavaFX, Firebird, JDBC, SQL или имён внешних таблиц.
3. В MVP реализуется только файловый (STXT) адаптер; он строит import model и не пишет в БД, не проводит документы и не вызывает JavaFX Controller.
4. Подтверждённый импорт выполняется атомарно через штатные application services и документную модель Order Management.
5. Будущий Firebird-адаптер (если потребуется) обязан формировать ту же source-neutral модель без изменения домена.
6. Новый Maven-модуль для границы не требуется, пока ответственность умещается в `tmp-order-management`.
7. Downstream Capability (Warehouse, Production, Cutting) зависят только от утверждённых агрегатов Order Management, не от канала поступления.

### Последствия

- домен остаётся единым для ручного ввода и импорта;
- адаптеры сменяемы без изменения агрегатов;
- запрет прямой persistence из UI/парсера усиливается;
- Firebird не тянет зависимости и схему в MVP.

### Связанные документы

- Order-Management-Specification.md (§27)
- TMP-Constitution.md
- ADR-003, ADR-004, ADR-019, ADR-028, ADR-030

# ADR-030

## Название

Incomplete Commercial Data Allowed Only in DRAFT.

### Статус

Accepted

### Контекст

Файловая выгрузка расчётной программы содержит номер заказа, позиции и спецификации, но не содержит полный набор коммерческих реквизитов заказа (`customerName`, `direction`, `currency`, `contractNumber`/`contractRef`, `objectName`/`siteRef`) и не содержит коммерческие реквизиты позиции (`productCode`, `name`). Для Order Intake MVP импорт должен создавать заказ и позиции без фиктивных коммерческих значений. Утверждение заказа или Draft Revision позиции без обязательных коммерческих полей недопустимо.

### Решение

1. Заказ в статусе `DRAFT` может временно не содержать обязательные коммерческие поля: `customerName`, `direction`, `currency`, `contractNumber`/`contractRef`, `objectName`/`siteRef`.
2. Позиция заказа в статусе `DRAFT` может временно не содержать: `productCode`, `name`. Отсутствие представляется `null` (не пустой строкой и не placeholder).
3. `externalPositionNumber` не является `productCode`. `materialName` строки спецификации не является наименованием Order Item.
4. Файловый импорт может создать неполный `DRAFT`-заказ и неполные `DRAFT`-позиции.
5. Фиктивные/заглушечные значения запрещены: `UNKNOWN`, `N/A`, `IMPORT`, `—`, «Изделие N», пустые системные stubs и значения, сконструированные из внешнего номера позиции.
6. Пользователь дополняет коммерческие данные вручную.
7. `ORDER_APPROVE` запрещён, пока обязательные коммерческие поля заказа не заполнены; ошибка утверждения должна перечислять отсутствующие поля.
8. `ORDER_ITEM_REVISION_APPROVE` запрещён, пока у позиции не заполнены `productCode` и `name` (и непустая корректная спецификация); ошибка должна перечислять отсутствующие поля («Код изделия», «Наименование изделия»).
9. После утверждения применяются обычные правила неизменяемости; утверждённая (`ACTIVE`) позиция не может иметь отсутствующие `productCode` или `name`. Позиция `CANCELLED` может хранить последнее состояние ранее неполного `DRAFT` (включая null); это не означает разрешение редактировать отсутствующие поля в `CANCELLED`.
10. Правило относится к доменной модели `DRAFT` и не зависит от формата STXT.

### Последствия

- импорт не требует placeholder-коммерции на уровне заказа и позиции;
- доменная валидация create/update DRAFT ослабляется только для коммерческих полей;
- approval остаётся строгим gate для заказа и для Draft Revision позиции;
- blocker `STAGE5-INTAKE-COMMERCIAL-DRAFT` закрыт как RESOLVED;
- item-level incompleteness реализуется в `STAGE5-052A` до Import Core.

### Связанные документы

- Order-Management-Specification.md (§27.7)
- ADR-029
- ADR-031
- `docs/development-control/BLOCKERS.md` (`STAGE5-INTAKE-COMMERCIAL-DRAFT`)

# ADR-031

## Название

Imported Order Lifecycle Rules — Uniform ACTIVE (Trusted Import as Creation Path Only).

### Статус

Accepted (final architecture decision for STAGE5-058; **implemented** in STAGE5-058)

### Контекст

Ранее рассматривались варианты с `OrderOrigin`, отдельными правилами для импортированного ACTIVE, import metadata / checksum duplicate protection и запретом новой Revision на импорте. Финальное бизнес-решение иное:

1. Импортированный из расчётной программы заказ **полностью доверенный** и после успешного импорта сразу `ACTIVE`.
2. **ACTIVE не зависит от способа создания** — поведение одинаково для ручного и импортного пути.
3. Импорт — **только способ создания**, не отдельная сущность и не отдельный lifecycle-тип заказа.
4. Изменение ACTIVE — **только через существующий механизм Revision**.

### Решение

#### 1. Единый ACTIVE (главный принцип)

Не существует различий между:

- `ACTIVE` после ручного `DRAFT → APPROVED → ACTIVE`;
- `ACTIVE` после import operation.

После перехода в `ACTIVE` применяются **одни и те же** инварианты, UI-правила, Document/Revision flow, Query API и контракты для Warehouse/Production.

**Запрещено** вводить признаки или сущности, создающие различие ACTIVE по происхождению:

- `OrderOrigin` / `creationSource` / `imported` flag;
- `ImportMetadata` / отдельные import-сущности;
- persistent `sourceType`, `importedAt`, `importedBy`, checksum storage как защита или бизнес-атрибут заказа;
- отдельные permissions / read-only правила «только для импорта».

(Фактические артефакты Order Intake MVP, противоречащие этому — в т.ч. checksum/`order_import_metadata` — **подлежат удалению или выводу из бизнес-контракта** в `STAGE5-058`, без замены другим origin-маркером.)

#### 2. Lifecycle

**Ручной путь:**

```text
Order:        DRAFT → APPROVED → ACTIVE
Order Item:   DRAFT → ACTIVE
Revision:     DRAFT → ACTIVE
Specification: становится ACTIVE (Immutable) вместе с ACTIVE Revision
```

**Импорт:**

```text
STXT → Import Core confirm (одна TX)
  ORDER_CREATE / ITEM_CREATE / REVISION_UPDATE
  → ORDER_ITEM_REVISION_APPROVE  (Item + Revision + Specification ACTIVE)
  → ORDER_APPROVE (import gates: client + ≥1 ACTIVE item)
  → ORDER_ACTIVATE
  → Order ACTIVE
```

- Долгоживущий `OrderStatus.IMPORT` **не вводится**.
- Долгоживущий import-`DRAFT` **не допускается**; промежуточный DRAFT существует только внутри TX до approve/activate.
- Прямая активация агрегатов в обход Document Engine **запрещена**.
- `IMPORT operation` — orchestration через существующие документы; конечное состояние = `ACTIVE`.
- Статус Revision: целевой enum `DRAFT | ACTIVE`. Specification «ACTIVE» = спецификация текущей ACTIVE Revision, Immutable.

#### 3. Правила импорта

1. Импорт создаёт ту же доменную структуру, что и ручной путь: Order → Item → Revision → Specification.
2. После успешного confirm все перечисленные уровни — `ACTIVE` (доверенный производственный эталон).
3. **Final STXT Contract (STAGE5-058):** выгрузка содержит номер/дату/клиента заказа и `productCode`/`name`/quantity изделия; ACTIVE import **требует** эти поля (placeholders запрещены). Коммерческие completeness-gates ADR-030 (`direction`/`currency`/`contractRef`/`siteRef` и т.п.) по-прежнему относятся к **ручным** переходам `ORDER_APPROVE` / утверждению Draft Revision и **не** блокируют import landing.
4. После landing поведение = обычный `ACTIVE` (п.1, п.5).
5. Файл может содержать **несколько** заказов; каждый становится отдельным Order (атомарно в одной confirm TX).

#### 4. Дублирование

**Единственная** проверка при импорте:

```text
orderNumber uniqueness
```

Если заказ с таким номером уже существует — импорт запрещён (понятное сообщение пользователю).

**Не создавать** отдельную защиту импорта (checksum, повтор файла, import metadata registry и т.п.).

#### 5. Immutable ACTIVE и Revision flow

`ACTIVE` всегда:

- не редактируется напрямую пользователем;
- не изменяется через `ORDER_UPDATE` / `ORDER_ITEM_UPDATE` / правку ACTIVE Specification;
- является производственным эталоном для Warehouse / Production.

Изменение содержимого ACTIVE:

```text
только через существующий механизм Revision
(ORDER_ITEM_REVISION_CREATE → draft update → approve → новая ACTIVE Revision)
```

Правило **одинаково** для ACTIVE, полученного вручную и через импорт. Запрет «новой Revision только для импорта» **отменён**.

#### 6. Влияние на модули

| Область | Влияние |
| --- | --- |
| Order Management | Landing import → ACTIVE; единые инварианты ACTIVE; RevisionStatus → `ACTIVE`; убрать origin/metadata-контракты |
| Document Engine | Без новых platform lifecycle статусов; import = orchestration штатных/целевых документов Order Management внутри TX |
| UI | Read-only для **любого** ACTIVE (прямое редактирование); Revision flow доступен как для ручного ACTIVE |
| Revision flow | Единый; импорт не имеет отдельной ветки |
| Warehouse (Stage 6) | Потребляет ACTIVE Order/Item + current immutable Specification через утверждённые контракты; **не** знает и **не** должен знать канал создания |
| Production | Downstream-контракт: ACTIVE Order → Order Item → current immutable Specification; **без** зависимости от Order Item Revision в состоянии Production (ADR-033); без import-специфики. Внутренняя Revision-модель OM сохраняется |

#### 7. Out of scope

- Реализация Stage 6/7;
- Firebird adapter;
- merge/overwrite / re-import-as-update;
- изменение Constitution document-driven model.

### Последствия

- упрощение модели: один ACTIVE, два пути **создания**;
- ADR-030 остаётся gate ручного утверждения; не создаёт «тип» ACTIVE;
- Warehouse/Production контракты проще и стабильнее;
- `STAGE5-058` реализовал код и схему по этому решению (включая отказ от checksum-import protection);
- до `STAGE5-058` DONE код мог создавать import-`DRAFT` — technical debt снят.

### Связанные документы

- Order-Management-Specification.md (§8, §9, §27)

# ADR-032

## Название

Material Responsibility Decision — No Separate Material Master.

### Статус

Accepted (Stage 6 Start Gate, 2026-08-06)

### Контекст

Ранее Warehouse Specification §10 и Rule 6 описывали Material как «единый мастер-объект платформы», владельцем которого является Order Management. Stage 5 MVP реализовал материалы только как атрибуты строк ACTIVE Specification (`materialCode`, `materialName`, `color`, `lengthMm`, `lineQuantity`, `unitOfMeasure`) без отдельного каталога, UUID или модуля Material Master.

Перед Stage 6 Warehouse требовалось финальное решение о владении материалами и отсутствии отдельного справочника.

### Решение

1. **Отдельный Material Master / модуль управления материалами в текущей версии TMP не создаётся.** Решение финальное для текущей архитектуры.

2. **Order Management** определяет, какие материалы нужны для изготовления изделия, через Item Specification (ACTIVE Revision). Order Management владеет:
   - заказом;
   - позициями заказа;
   - редакциями;
   - спецификациями изделий;
   - материалами **в контексте спецификации изделия**.

   Order Management **не** владеет: складскими остатками, партиями хранения, ячейками, движениями материалов, резервированием.

3. **Warehouse** использует материалы, определённые в Order Management Specification. Warehouse хранит только **складское состояние** материалов (Stock Position, Batch, Movement, Reservation, Warehouse Operation). Warehouse **не** создаёт и **не** изменяет данные спецификации; **не** владеет мастер-данными материалов; **не** выполняет сопоставление материалов.

4. **Material Mapping** — пользовательский механизм сопоставления внешнего наименования материала из расчётной программы (СуперОкна) с нормализованным значением TMP. Пример:

   ```text
   "Профиль VEKA 103.211 Белый"  →  "VEKA 103.211 WHITE"
   ```

   Правила:
   - сопоставление настраивается пользователем;
   - отсутствие сопоставления **не блокирует** импорт;
   - Warehouse **не** отвечает за сопоставление;
   - Production использует нормализованные данные.

5. **Production interaction (целевой поток; уточнено ADR-033):**

   ```text
   Order Management: ACTIVE Order → Order Item → current immutable Specification
           ↓ (Public Query API; Revision — внутренняя модель OM)
   Production: доступные заказы → изделия → количество → Specification
           ↓ (расчёт потребности)
   Production → Warehouse: запрос доступности / инициирование Transfer / Consumption
           ↓
   Warehouse: наличие, доступность; владеет складскими документами и Stock Position
   ```

6. **Material identity для Warehouse** — составной идентификатор из полей ACTIVE Specification: `materialCode`, `materialName`, `color`, `unitOfMeasure` (и `lengthMm` где применимо). Отдельный каталог материалов **не требуется**.

7. Warehouse Public API оперирует **MaterialReference** (поля спецификации / нормализованный запрос Production), а не UUID master-объекта Material.

### Последствия

- Supersedes интерпретацию Warehouse Specification §10 «Material — единый мастер-объект» и Rule 6 «Order Management — владелец Material master»;
- Stage 6 Warehouse стартует без Material catalog; потребление из ACTIVE Specification;
- в ADR-006 и ADR-012 термин «Material» означает material identity из спецификации или запроса Production, а не master-entity;
- реализация Material Mapping — отдельная задача (не Warehouse; вне Production);
- Production Specification: OM владеет Specification; Production-facing path не требует Order Item Revision (ADR-033);
- основной принцип No Separate Material Master сохраняется.

### Связанные документы

- Order-Management-Specification.md (§3, §20, §28)
- Warehouse-Specification.md (§4, §10, §23, Rule 6)
- Stage 6 Manifest (`STAGE-6-WAREHOUSE.md`)
- ADR-031
- ADR-033

# ADR-033

## Название

Production Order-Level Workflow with Item-Owned State.

### Статус

Accepted

### Контекст

Пользователю удобно принимать и отменять производство **заказа целиком**, видеть общий статус заказа и не работать с техническими Revision. При этом Constitution и ADR-017 требуют, чтобы хранимое производственное состояние оставалось привязанным к Order Item, а вычисляемые агрегаты заказа не становились отдельным источником истины (ADR-020).

Старая Production Spec v1.1 связывала состояние с Order Item Revision и допускала partial launch / READY_FOR_PRODUCTION как persisted status, что усложняло UX и протекало во внешний контракт.

### Решение

1. **Пользовательский workflow — order-level:** команды «Принять в производство» и «Отменить производство заказа» применяются ко всему ACTIVE Order.
2. **Хранимое состояние — item-owned:** Production хранит статус и количества по `Order Item ID` (вместе с `Order ID`).
3. **Order Production View вычисляется** из item states и не хранится как источник истины.
4. **Отдельный Production Order не создаётся.**
5. **Downstream-контракт Production не зависит от Order Item Revision:** Production получает `ACTIVE Order → Order Item → current immutable Specification` + stable opaque `Specification ID` через Public Query API Order Management. Внутренняя Revision-модель OM сохраняется и не обязана протекать в Production state / documents.
6. При **Принять в производство** Production фиксирует `Specification ID` (Production Specification Reference) и далее не переключается автоматически на новую current Specification OM.
7. **`READY_FOR_PRODUCTION` не обязателен** как persisted status; проверка материалов не является prerequisite принятия в производство.
8. Частичный запуск отдельных позиций не является основным UX; частичный выпуск количеств во времени допускается.
9. Cutting Plan links: `MaterialReference → CuttingPlanId` (0..N на Order Item); не одно поле на всю позицию.

### Последствия

- ADR-017 сохраняется (Order Item — единица производственного состояния);
- ADR-018 / внутренняя Revision OM сохраняются;
- ADR-020 усиливается для order-level view;
- Production Specification v2.1 и Stage 7 Manifest следуют этой модели;
- Stage 5 код не переписывается этим ADR; меняется межмодульный контракт документации.

### Связанные документы

- Production-Specification.md (v2.1)
- Order-Management-Specification.md (Production-facing contract)
- ADR-017, ADR-018, ADR-020, ADR-031, ADR-032

# ADR-034

## Название

Cutting Plan as Independent Non-Revision Recommendation.

### Статус

Accepted

### Контекст

Модель Cutting Plan Revision и жёсткий lifecycle `APPROVED → IN_USE → COMPLETED`, управляемый событиями Production, усложняет Stage 7/8 и противоречит принятой простой модели: карта рекомендательна, Production независим от Stage 8, новый расчёт = новый документ.

### Решение

1. Cutting Plan — самостоятельный бизнес-документ Cutting Optimization (независимость ADR-023 сохраняется по смыслу).
2. **Модели Cutting Plan Revision нет.** Каждый Cutting Plan — отдельный документ. После утверждения/использования карта не редактируется; другой расчёт = **новый Cutting Plan**.
3. Cutting Plan **необязателен** (ADR-024 сохраняется).
4. Карта может включать позиции одного или нескольких заказов; связь явная через Order ID / Order Item ID.
5. Для длинномерных материалов Cutting Plan — **рекомендуемый/default** источник плановой потребности; не безусловный источник фактического складского движения. Мастер может скорректировать шаблон перемещения и факт.
6. Production хранит связи `MaterialReference → Cutting Plan ID` (0..N на Order Item) и **не управляет** lifecycle Cutting Plan.
7. События Production не обязаны переводить карту в `IN_USE` / `COMPLETED`.
8. ADR-034 меняет lifecycle/версионирование Cutting Plan; **не отменяет** подробную бизнес-функциональность Cutting Optimization (Source Bar, Cut Piece, Calculation Result, стратегии, редактор, export и т.д.).

### Последствия

- Supersedes ADR-023, ADR-025, ADR-026, ADR-027;
- Cutting Optimization Specification сохраняет подробный Stage 8 scope без Revision-модели;
- Production не зависит от runtime Stage 8.

### Связанные документы

- Cutting-Optimization-Specification.md
- Production-Specification.md
- ADR-024

# ADR-035

## Название

Production Material Transfer and Plan/Fact Consumption.

### Статус

Accepted

### Контекст

Пассивная рекомендация перемещения без пользовательского шаблона и отсутствие явного plan/fact при выпуске не соответствуют согласованному UX мастера производства. Нужна чёткая граница: Production инициирует, Warehouse владеет складом и документами.

### Решение

1. Production формирует **редактируемый шаблон** перемещения материалов (не пассивный-only recommendation).
2. После подтверждения создаётся **Warehouse-owned** Transfer через Warehouse Application/Document commands (send → IN_TRANSIT → receive); Production не владеет складским документом и не меняет Stock Position.
3. Команда «Подтвердить получение» может быть в UI Production, но receive выполняет Warehouse-owned document operation.
4. Production Release хранит **plan и fact** расхода; Warehouse Consumption (Warehouse-owned document) списывает фактическое количество со склада производства.
5. Warehouse Public Query API — только чтение; mutating операции не являются Public Query API (Constitution принцип 28 / ADR-003 / ADR-004).
6. Недостаток материала на складе производства блокирует проведение Release; отрицательные остатки запрещены; Specification/Cutting Plan из-за факта не изменяются.
7. Проведение Release и связанного Consumption должно быть атомарным (единая TX orchestration). Механизм атомарности — ADR-036. Данный ADR остаётся принятой бизнес-границей и **не** supersede.

### Последствия

- Warehouse Spec integration уточняется без переделки Stage 6 core;
- Production Spec v2.2 §13–§15, §21;
- Security: переиспользование Warehouse permissions где возможно;
- atomicity mechanism → ADR-036.

- Production-Specification.md (v2.2)
- Warehouse-Specification.md

- ADR-010, ADR-032, ADR-034, ADR-036

# ADR-036

## Название

Shared ACID Transaction for Cross-Capability Document Orchestration.

### Статус

Accepted

### Контекст

Одна бизнес-операция TMP может требовать проведения нескольких бизнес-документов разных Capability — в частности Production Release и Warehouse Consumption. Document Engine гарантирует атомарность одной lifecycle-операции документа и его processor. Без явного контракта оставалась неопределённость: можно ли атомарно провести два таких документа в одной локальной транзакции модульного монолита, не вводя Saga, eventual consistency или distributed transaction.

Constitution принцип 19 требует, чтобы бизнес-операция выполнялась полностью либо не выполнялась вовсе, если иное явно не определено спецификацией. Принципы 15, 18, 21 и 28 требуют сохранить ownership: единая database transaction не означает общую модель владения данными.

### Решение

1. TMP является модульным монолитом с общей локальной transaction infrastructure для business persistence.
2. Если одна бизнес-операция требует атомарного проведения документов нескольких Capability, application orchestrator может открыть одну общую ACID-транзакцию.
3. Document Engine lifecycle operations обязаны присоединяться к существующей совместимой транзакции через REQUIRED semantics. При отсутствии внешней транзакции lifecycle operation открывает собственную.
4. Каждый Document Processor остаётся владельцем логики своей Capability и выполняется внутри той же транзакции, к которой присоединилась lifecycle operation.
5. Capability ownership не меняется. Production владеет Production-документами и production state; Warehouse владеет Consumption, Movement и Stock Position; Document Engine владеет metadata и lifecycle journal.
6. Межмодульные изменения по-прежнему выполняются только через бизнес-документы владельцев данных. Никакая Capability не получает прямой repository/table access другой Capability.
7. Ошибка любого участника общей операции приводит к rollback всей транзакции, включая document metadata, lifecycle journal и capability-owned изменения всех участников.
8. After-commit Domain Events публикуются только после общего успешного commit внешней транзакции и не публикуются после rollback, даже если внутренняя lifecycle operation уже вернула успех внутри ещё не зафиксированной транзакции.
9. Общая транзакция допускается только если участники используют один совместимый transaction manager / database transaction boundary.
10. Данный ADR **не** гарантирует атомарность разных баз данных, внешних сервисов, message brokers или удалённых HTTP services.
11. Distributed transaction / 2PC / Saga в текущую архитектуру не вводятся. Document Engine не предоставляет business-specific orchestrator и не знает смысла конкретной orchestration.

### Последствия

- Production Release и Warehouse Consumption проводятся в одной локальной ACID-транзакции application orchestrator (Production Spec §21).
- Document Engine Specification фиксирует multi-document / ambient transaction contract (v1.2).
- ADR-035 остаётся бизнес-границей Release/Consumption; данный ADR задаёт только механизм атомарности.
- Stage 7 Start Gate atomicity считается доказанным при наличии integration proof на общей PostgreSQL transaction.

### Связанные документы

- TMP-Constitution.md (принципы 15, 18, 19, 21, 28)

# 6. Правила внесения изменений

При изменении архитектуры TMP необходимо соблюдать следующие правила.

1. Если изменяется существующее архитектурное решение, соответствующий ADR получает статус **Superseded**.

2. Новое решение оформляется отдельным ADR с новым номером.

3. Номер ADR никогда не изменяется и не используется повторно.

4. Удаление ADR запрещено.

5. Все новые Capability должны быть проверены на соответствие существующим ADR.

6. Если новое архитектурное решение противоречит существующему ADR, сначала должен быть создан новый ADR, заменяющий прежний.

> **Architecture Rule**  
> Архитектурные решения являются частью контракта платформы. Нарушение принятого ADR допускается только после его официального пересмотра.

---

# 7. Принципы использования ADR

Архитектурные решения не должны содержать:

- описание пользовательских интерфейсов;
- описание бизнес-процессов;
- описание структуры базы данных;
- описание конкретной реализации алгоритмов.

Для этих целей используются специализированные спецификации Capability.

Каждый ADR отвечает только на четыре вопроса:

- какую проблему необходимо решить;
- какое решение принято;
- почему принято именно это решение;
- какие последствия оно имеет.
