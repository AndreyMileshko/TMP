# AGENTS.md — TOP Manufacturing Platform (TMP)

## 1. Назначение и приоритет правил

Этот файл задаёт постоянные правила работы AI-агентов (Cursor Agent и других совместимых инструментов) с кодовой базой TOP Manufacturing Platform (TMP).

Приоритет источников требований:
1. Явные указания разработчика в текущей задаче.
2. Утверждённые спецификации и архитектурные документы TMP в репозитории.
3. Этот файл `AGENTS.md`.
4. Существующая реализация и общепринятые инженерные практики.

Если требования противоречат друг другу, не выбирать трактовку самостоятельно: описать противоречие и запросить решение. Не считать предположения утверждёнными бизнес-правилами.

## 2. Контекст проекта

TMP — платформа управления производством.

Технологический стек:
- Java 21;
- Maven;
- JavaFX;
- PostgreSQL;
- модульный монолит;
- Capability Engine для подключения функциональных возможностей.

Перед изменениями изучай фактическую структуру репозитория, `pom.xml`, существующие модули, тесты и относящиеся к задаче документы. Не предполагай, что структура или состояние кода совпадают с предыдущей сессией.

## 3. Архитектурные инварианты

Следующие правила нельзя менять без явного согласования с разработчиком и обновления соответствующей спецификации:

- Изменения бизнес-состояния оформляются документами. Не изменяй состояние бизнес-объектов обходными путями.
- Позиция заказа — ключевой объект предметной модели.
- Зафиксированная спецификация заказа неизменяема. Не редактируй её задним числом; изменения должны проходить предусмотренный бизнес-процесс.
- Списание материалов производится только со склада производства.
- Значимые бизнес-операции должны быть аудируемыми.
- Сохраняй архитектуру модульного монолита и контролируй зависимости между модулями.
- Не допускай, чтобы нехватка материалов сама по себе блокировала запуск производства, если это противоречит утверждённой логике Production.
- Не вводи механизм Revision для производственного запуска без отдельного архитектурного решения.

## 4. Известные решения и спецификации

Сверяйся с актуальными документами в репозитории. Ниже перечислены известные базовые решения; при расхождении с более новой утверждённой спецификацией остановись и сообщи о нём.

### Platform Core
- Базовая архитектура платформы и общие инфраструктурные механизмы.
- Документы являются основным механизмом фиксации бизнес-изменений.

### Capability Engine
- Функциональные возможности подключаются через единый механизм Capability Engine.
- Не создавай параллельный механизм регистрации или подключения возможностей без согласования.

### Warehouse
- Основные операции: приход, перемещение, списание и резервирование.
- Списание материалов допускается только со склада производства.
- Резервирование носит предусмотренный спецификацией характер; не меняй его семантику самостоятельно.

### Production
- Статус готовности к производству: `READY_FOR_PRODUCTION`.
- Нехватка материалов не блокирует перевод в готовность к производству сама по себе.
- Повторный запуск оформляется новым заказом.
- Не вводи Revision без утверждённого изменения требований.

### Cutting Optimization
- Жизненный цикл карты раскроя: `DRAFT → APPROVED → IN_USE → CLOSED`.
- Карта раскроя может охватывать несколько заказов.
- Остатки склада не учитываются при построении карты раскроя, если актуальная спецификация не устанавливает иное.

### Цвета и конфигурации
- Справочник цветов и сопоставления должны соответствовать утверждённым данным.
- Двойной цвет задаётся парой «внутри/снаружи» на уровне заказа.
- Не изменяй правила формирования цвета без проверки соответствующей спецификации и тестов.

## 5. Рабочий процесс агента

Для каждой задачи придерживайся последовательности:

1. **Понять задачу.** Зафиксировать ожидаемый результат и критерии готовности.
2. **Исследовать проект.** Найти связанные классы, модули, интерфейсы, миграции, тесты и спецификации. Использовать поиск по репозиторию, а не полагаться только на названия из запроса.
3. **Проверить ограничения.** Определить затрагиваемые архитектурные инварианты, обратную совместимость и возможные побочные эффекты.
4. **Составить план.** Для локальной и однозначной задачи можно кратко обозначить план и сразу приступить. Для архитектурных изменений, изменений схемы БД, публичных контрактов, бизнес-статусов или межмодульных зависимостей сначала представить план и дождаться подтверждения.
5. **Реализовать минимально достаточное изменение.** Не переписывать несвязанные части системы.
6. **Проверить.** Запустить релевантные тесты и Maven-команды, проверить diff и отсутствие случайных изменений.
7. **Отчитаться.** Перечислить изменения, проверки, результаты и оставшиеся риски.

Если постановка неполная, сначала изучи код и документацию. Задавай уточняющий вопрос только тогда, когда без решения разработчика нельзя безопасно продолжить.

## 6. Правила изменения кода

- Сначала используй существующие абстракции, сервисы, репозитории, фабрики, обработчики документов и механизмы аудита.
- Не дублируй функциональность и не создавай сущности, пока не проверил, нет ли уже подходящего объекта.
- Не меняй публичные API, контракты модулей, форматы документов и схему БД без обоснования и согласования.
- Не добавляй Maven-зависимости без необходимости; объясняй назначение каждой новой зависимости.
- Не размещай бизнес-логику в JavaFX-контроллерах, если в проекте предусмотрены отдельные сервисы или слои.
- Соблюдай существующие соглашения проекта по именованию, пакетам, логированию, обработке исключений и транзакциям.
- Не подавляй исключения и не заменяй ошибки пустыми результатами без явно определённой бизнес-семантики.
- Не оставляй заглушки, фиктивные реализации, `TODO` или временные обходы вместо заявленной функциональности. Если полноценная реализация невозможна, явно укажи это.
- Не удаляй существующую функциональность ради упрощения новой реализации.
- Не изменяй пользовательские данные, реальные БД или внешние среды без прямого разрешения.
- Не выполняй опасные Git-команды (например, `reset --hard`, принудительный push, удаление веток) без прямого разрешения.

## 7. База данных и документы

- Проверяй транзакционные границы и атомарность операций.
- Учитывай конкурентный доступ и повторное выполнение команд.
- Изменения схемы PostgreSQL оформляй предусмотренным в проекте механизмом миграций.
- Не изменяй уже применённые миграции; создавай новую миграцию, если проект использует версионирование схемы.
- Проверяй ограничения целостности, внешние ключи, уникальность и индексы.
- Документы должны сохранять историю и аудит в соответствии с архитектурой TMP.
- Не допускай прямого изменения складских остатков в обход складских документов.

## 8. Тестирование и критерии готовности

Задача не считается завершённой только потому, что код написан.

По возможности выполняй:
- компиляцию затронутого Maven-модуля;
- релевантные unit-тесты;
- интеграционные тесты для БД и межмодульного взаимодействия;
- полный Maven build, если это разумно по времени и состоянию проекта;
- проверку diff на случайные, форматирующие и несвязанные изменения.

Не заявляй, что тесты пройдены, если они не запускались. Если тесты невозможно запустить, укажи причину и что именно осталось непроверенным.

## 9. Работа с моделями в Cursor

Выбирай модель по сложности задачи и доступному бюджету:
- **Composer** — повседневная реализация, локальные исправления, тесты, небольшие рефакторинги.
- **Grok** — анализ архитектуры, сложные межмодульные изменения, трудные дефекты и задачи, требующие более глубокого рассуждения.
- **Auto** — для обычных задач, когда ручной выбор модели не даёт явного преимущества.

Не используй более дорогой режим рассуждения для простых изменений. Не запускай несколько агентов на изменение одних и тех же файлов одновременно. Для параллельной работы используй отдельные Git-ветки или worktrees и заранее определяй границы изменений.

## 10. Формат итогового отчёта

В конце каждой задачи предоставляй краткий отчёт:

1. **Результат:** что реализовано.
2. **Изменённые файлы:** список с кратким назначением.
3. **Архитектурные решения:** только если они принимались.
4. **Проверки:** точные команды и фактические результаты.
5. **Ограничения и риски:** что осталось нерешённым или непроверенным.
6. **Следующий шаг:** только если он действительно необходим.

## 11. Главный принцип

AI Agent — исполнитель и технический помощник, но не владелец архитектуры и бизнес-правил TMP. Он обязан изучать существующую систему, сохранять утверждённые инварианты, вносить минимально необходимые изменения и подтверждать результат проверками. Существенные архитектурные и бизнес-решения остаются за разработчиком.
